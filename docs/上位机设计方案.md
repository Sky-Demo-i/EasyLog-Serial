## 1. 背景与目标

### 1.1 为什么现有工具不够用

| 现成方案 | 能做什么 | 差在哪 |
| --- | --- | --- |
| SSCOM / XCOM / 友善 | 收发字节、HEX、定时发送 | 把日志当纯文本；不认 level/tag；ANSI 颜色变乱码；长日志卡 |
| Tera Term / PuTTY | 正确渲染 ANSI、记录日志 | 没有结构化过滤；没有错误快照；不是为日志设计 |
| comNG | 语法高亮、长日志、条件中断 | 不懂 EasyLogger 字段；无级别/tag 语义过滤；无回放/快照体系 |
| Serial Studio | 仪表盘、曲线 | 面向数值遥测，不是文本日志 |

**结论：做一款"EasyLogger 日志工作台"，而不是第 N 个串口助手。**

### 1.2 产品目标

- **看得清**：级别、Tag、函数:行、消息分列显示，颜色可读，V/D 不淹没 I/W/E。
- **找得到**：按级别阈值、Tag、关键字/正则过滤；长日志里秒级定位。
- **留得住**：全程落盘、可回放；出错时一键保存"前 N 秒现场"。
- **连得稳**：921600 连续跑 24 小时不丢、不卡、不崩。
- **装得下**：单文件安装包，双击即用，不依赖运行环境。

### 1.3 非目标（首版不做）

- 不做通用 Modbus/PLC 主站（后续可加插件）。
- 不做 IDE、不做编译下载。
- 不做云端日志平台（预留导出即可）。

## 2. 真实日志格式拆解

### 2.1 三行样例的字段

原始行（`<ESC>` 表示 0x1B；样例 1 在实际抓包里前面还有 `[16:02:22.722]收←◆`，这里为看清设备输出已省略）：

```
<ESC>[34;22mV/TRK    (185 jm_pal_get_utc_time)[480],1970-1-1 8:32:54, 480<ESC>[0m
<ESC>[34;22mV/TRK    (360 jm_sensor_sc7a20h_get_xyz)raw:80 07 60 09 70 c4, X = 30  Y = 37  Z = -239 <ESC>[0m
<ESC>[32;22mD/TRK    (255 track_master_rollover_norm_check)x:y:z=1:22:20 over:2 acc:243 stage_t:1,  (30:37:-239)<ESC>[0m
```

| 字段 | 样例 1 | 样例 2 | 样例 3 | 说明 |
| --- | --- | --- | --- | --- |
| 主机时间 | `16:02:22.722` | 无 | 无 | **抓包工具加的**；只在新数据段首行出现，不是每行都有 |
| ANSI | `34;22` | `34;22` | `32;22` | SGR：蓝 / 绿；行尾 `0` 复位 |
| 级别 | `V` | `V` | `D` | 单字母 + `/`，A/E/W/I/D/V |
| Tag | `TRK` | `TRK` | `TRK` | 后面是**填充空格**，宽度不固定 |
| 行号 | `185` | `360` | `255` | `(line func)` 中的第一段 |
| 函数 | `jm_pal_get_utc_time` | `jm_sensor_sc7a20h_get_xyz` | `track_master_rollover_norm_check` | 无括号、无文件路径 |
| 消息 | `[480],1970-1-1 8:32:54, 480` | `raw:80 07 ... Z = -239 ` | `x:y:z=1:22:20 ... (30:37:-239)` | 任意文本，可含 `[] , : =` |

### 2.2 五个关键结论

1. **真正可依赖的结构只有 `LEVEL/TAG (line func)`**，其后全部是消息，不能再按分隔符硬切。
2. **设备没有输出时间字段**。`1970-1-1 8:32:54` 只是消息内容，说明 RTC 未校准；时间基准只能由上位机打。
3. **颜色不能反推级别**。样例里 `V` 是蓝色（34）、`D` 是绿色（32），与"常识配色"不一致；**必须以字母为准**。
4. **Tag 填充宽度不固定**。解析用 `\s*`，不能写死 4 个空格。
5. **`[16:02:22.722]收←◆` 是抓包工具的前缀，且只在新数据段首行出现**——同一次 `read()` 里的多行只有第一行带时间戳。导入旧日志时不要假设"每行都有时间"，精确时间只能靠本工具采集时逐行打。

### 2.3 边界情况清单

| 情况 | 处理策略 |
| --- | --- |
| 串口分片（一行跨多个 USB 包） | 按 `\n` 组包；`\r\n` / `\n` / `\r` 都兼容 |
| 抓包前缀只出现在首行 | 导入时首行赋值，其余按到达顺序还原；精确时间以本工具采集为准 |
| 行尾 ANSI 被截断 | 保留残余，等下一包；超时 200ms 强制成行 |
| `elog_raw()` 输出 | 无前缀，降级为"未解析"样式，原文照显 |
| `elog_hexdump()` 多行块 | 识别 `[0000] xx xx ...` 形态，折叠成一行，可展开 |
| ESC 被吞（只剩 `[34;22m`） | 行首命中时按残缺 ANSI 处理（见原型） |
| UTF-8 / GBK 混用 | 默认 UTF-8，设置项可切 GBK，非法字节替换显示 |
| 超长行（>8KB） | 强制截断并计数，防止内存失控 |
| 空行 / 纯 `\r` | 可配置"保留/丢弃"，默认丢弃 |

## 6. 技术架构

### 6.1 数据管线

```
[串口读线程] --bytes--> [SPSC 环形缓冲] --chunk--> [组包/解析线程]
       |                                                  |
       |                                                  v
       +--> [原始落盘线程] <---- raw chunks -------- [记录队列]
                                                          |
                              +---------------------------+-------------------+
                              v                                               v
                   [会话写盘线程 JSONL]                          [UI 批处理 每 50ms]
                                                                              |
                                                                     [过滤/索引]
                                                                              |
                                                                     [虚拟表格渲染]
```

### 6.2 线程与背压

| 线程 | 职责 | 阻塞策略 |
| --- | --- | --- |
| Serial Reader | 读串口、打时间戳、写环形缓冲 | **绝不阻塞**；缓冲满则丢弃并计数 |
| Framer/Parser | 组行、ANSI、解析、入队 | 队列满则阻塞读线程（触发丢弃计数） |
| Raw Writer | 原始字节顺序落盘 | 队列满 → 告警；优先保 raw |
| Session Writer | JSONL 落盘 | 队列满 → 丢弃 JSONL 并记录缺口，raw 不受影响 |
| UI Batch | 每 50ms 批量取记录 | UI 慢时丢显示批次，**不影响落盘** |

原则：**显示可以丢，文件不能丢；文件保不住时，raw 优先。**

### 6.3 数据模型

```ts
interface LogRecord {
  seq: number;          // 全局递增
  rxTs: number;         // 主机单调时钟（ms），用于 ΔT
  wallTs: number;       // 主机墙钟（epoch ms）
  deltaMs: number;      // 距上一行
  level: 'A'|'E'|'W'|'I'|'D'|'V'|'?';
  tag: string;
  line: number;
  func: string;
  message: string;      // 去 ANSI
  raw: string;          // 含 ANSI
  ansi: string[];       // SGR 参数，用于还原设备配色
  parsed: boolean;
}
```

### 6.4 性能预算

| 指标 | 目标 |
| --- | --- |
| 吞吐 | 5,000 行/秒 @ 平均 80B（约 3.2 Mbps 等效） |
| 延迟 | 串口 → 界面 < 100ms |
| 内存 | 20 万行驻留 < 150MB；环形缓冲上限可配 |
| 搜索 | 20 万行正则 < 200ms |
| 长稳 | 24 小时连续录制，内存增长 < 5% |
| 启动 | < 1.5s（冷启动） |

> 数学上 2 Mbps ≈ 250 KB/s，对现代机器不是瓶颈；真正的瓶颈是**逐行刷新 UI**，所以必须批量 + 虚拟列表。

## 7. 解析器规格

### 7.1 预处理顺序

1. 去行尾 `\r`。
2. 可选剥离抓包前缀：`^\[\d{2}:\d{2}:\d{2}\.\d{1,3}\](收←◆|发→◇)?`。
3. 可选剥离设备时间前缀：`^\[(日期时间|时间)\]`，记入 `dev_time`。
4. ANSI 剥离（同时记录 SGR），残缺 ANSI 兼容。
5. 结构匹配，失败则降级为未解析。

### 7.2 匹配规则（按顺序尝试）

```regex
# 1) 完整格式：LEVEL/TAG (line func)message
^(?<level>[AEWIDV])/(?<tag>[A-Za-z0-9_.\-]+)\s*\((?<line>\d+)\s+(?<func>[A-Za-z_]\w*)\)(?<msg>.*)$

# 2) 无 line/func：LEVEL/TAG message
^(?<level>[AEWIDV])/(?<tag>[A-Za-z0-9_.\-]+)\s+(?<msg>.*)$

# 3) 无 tag：LEVEL/ message
^(?<level>[AEWIDV])/\s*(?<msg>.*)$
```

### 7.3 可配置性

- 内置预设"EasyLogger 默认"，另提供"自定义模板"：用户可用命名组写正则，界面里粘贴一行样例实时预览解析结果。
- 原因：`elog_set_fmt()` 可以关掉 level/tag/time/func/line 中任意字段，固件一改格式就变。**解析器必须可配置，且永远保留"未解析降级"通道。**

### 7.4 参考实现与测试

[`tools/elog_parse.py`](../tools/elog_parse.py) 已实现上述逻辑，并通过自测：

```bash
python tools/elog_parse.py --selftest   # 3 条真实样例 + 6 类变体
python tools/elog_parse.py --demo       # 表格输出
python tools/elog_parse.py capture.txt --json
```

覆盖：真实三行、抓包前缀、ESC 丢失、7 字节分片、无 line/func、无 tag、`elog_raw` 降级、设备时间前缀、空行。
移植到 Rust/C++/C# 时，以该文件的 `parse_line` 与 `LineFramer` 为准。

## 8. 存储与会话

### 8.1 会话包 `.elog`（zip）

```
session.elog
├── meta.json      # 版本、开始时间、端口、波特率、解析预设、应用版本
├── raw.bin        # [u32 len][u64 ts][bytes] ... 原始字节，保真
└── records.jsonl  # 每行一条 LogRecord，便于 grep/分析
```

- 滚动：单文件 256MB 或 1 小时，自动切分，文件名带序号。
- 崩溃安全：先写 `.part`，正常关闭时改后缀；启动时提示恢复。
- 回放：以 `records.jsonl` 为准；raw 用于"原始视图"和二次解析。

### 8.2 为什么双写

- 只存文本：丢 ANSI/分片信息，无法复现。
- 只存 raw：每次打开都要重新解析，搜索慢。
- 双写：raw 保真，jsonl 保快。

| **Qt 6 Widgets（C++）** | 中 | 高 | ~30–40MB | Win/mac/Linux | ⚠️（Qt6 不支持，需 Qt 5.15） | 中（单一 C++） |
| **C# WPF（.NET 8）** | 最快 | 高 | ~15–20MB | ❌（Avalonia 可跨） | ❌（.NET 8）；.NET Framework 4.8 可 | 低 |
| **Electron** | 最快 | 中 | ~120MB | ✅ | ⚠️ | 中 |

### 推荐

- **默认：Tauri 2**。串口与解析放 Rust（无 GC、线程可控），界面用 React（表格/筛选迭代快），安装包小，天然跨平台。适合做成长期产品。
- **若团队只写 C++：Qt 6 Widgets**（要支持 Win7 则用 Qt 5.15）。QSerialPort + `QAbstractTableModel` + 自绘委托，性能足够，部署用 windeployqt。
- **若只做 Windows 10/11 且想两周出活：C# WPF**。开发效率最高，文本性能好，单文件发布简单。

> 决策前必须确认：**客户现场是否还有 Windows 7**。这一条会直接排除 Tauri 和 .NET 8。
